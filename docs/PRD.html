Loops: loop testing progress dashboard

Product requirements for turning the daily “Loop test daily Look Ahead” emails into one dashboard everyone can read.

Draft v0.217 Oct 2026Owner: Jaime BourneProject: Norfolk Vanguard ICT loop testing

1. Problem

Loop testing progress reaches about 25 people across Aker Solutions, Siemens Energy, RWE and Drydocks World as a daily email. Each email restates the full status table and quotes every earlier day underneath it. By 17 Oct the thread holds seven messages and runs to over 2,000 lines of text.

That format makes three things hard:

  • Trends are invisible. Each email shows today's number and a one-line delta. Spotting that Punch B has gone from 20% to 46% of CWA records means reading six emails side by side.
  • Mismatches hide in prose. The gap between field-complete loops and CWA records, and the loops counted in CWA before they are fully tested, only appear as comment text.
  • Constraints lose their history. Wi-Fi, operator access and SCADA availability come back every day with slightly different wording, and nothing records when each was raised or whether it is fixed.

Product goal: anyone on the distribution list can open one page and see in under a minute where testing stands, what changed since yesterday, and what is blocking closure.

3. Goals and non-goals

Goals

  • One page with the latest KPIs, deltas against the previous report, and the trend since the first report.
  • Calculated findings: PB share, reconciliation backlog, I/O rate by system, work in progress.
  • System status board and a constraints log that keeps each constraint's raised date and status.
  • A searchable register of the loop lists published in the thread.
  • Repeatable: a new email goes in source/, one script rebuilds the data.

Non-goals for v1

  • Replacing the master tracker (SharePoint Excel) or CWA as the system of record.
  • Editing data in the dashboard.
  • Live connections to CWA, the tracker or SCADA. These are v3 (see roadmap).

5. Data model

data/daily_reports.json holds one record per report. Fields:

FieldMeaning
progressThroughDay the figures describe (the email is sent the next morning).
commencedHW loop references with any testing started (cumulative).
fieldCompleteAll HW I/O in the loop reference recorded complete.
partial / noIoYetCommenced but not complete, split by whether any I/O is done.
cwaOk / cwaPb / cwaTotalCPCLs recorded in CWA as OK, as Punch B, and both.
awaitingCwaField complete but still OS (outstanding) in CWA.
partialAlreadyInCwaPartially tested but already OK/PB in CWA.
ioBySystem / cpclBySystemIndividual I/O completed and CPCLs signed that day, by system.
remainingScopeLoop refs and I/O left per system, where a report states them.

It also holds systems, constraints and milestones. scripts/build_data.py parses the loop-list tables straight from the .eml into data/loop_register.json and bundles everything into data/data.js for the page.

7. Metric definitions

  • Punch B share = cwaPb / cwaTotal.
  • Work in progress = commenced − fieldComplete.
  • Refs to reconcile = awaitingCwa + partialAlreadyInCwa.
  • Unexplained CPCLs = cwaTotal − (fieldComplete − awaitingCwa + partialAlreadyInCwa). It should be zero. It has been 1–2 on every day since 13 Oct.
  • Non-82 I/O = daily I/O excluding System 82 electrical panels, which carry about 20 I/O per CPCL against 1–5 for instrument loops.

8. Hosting and access

The dashboard is hosted on Vercel as a static site straight from orangejam72/loops.

ConcernApproach
BuildNone. data/data.js is generated locally by scripts/build_data.py and committed. Vercel serves the repo root as-is (Framework Preset: Other).
ReleasesA push to the production branch deploys to production. Other branches get preview URLs to check before merging.
Routes/ dashboard, /prd this document, /readme setup guide. Clean URLs, no trailing slash.
Data exposure.vercelignore keeps source/ and scripts/ off the deployed site, so the raw email and its contact details are never served (R13).
AccessVercel Deployment Protection (Vercel Authentication or password) limits viewers to invited people. X-Robots-Tag: noindex and robots.txt block indexing (R14).
Freshnessdata/ is served with must-revalidate, so viewers get a new report straight after deploy.

9. Success measures

  • The daily email can link to the dashboard instead of quoting the full table history.
  • Updating takes under 5 minutes: drop the email in, run the script, publish.
  • Reconciliation gaps are raised before the email goes out, and the unexplained-CPCL count reaches zero.
  • Constraints carry a status, so “still open after N days” can be seen at a glance.

11. Risks and open questions

  • Total scope is not in the emails. Without it the dashboard cannot show percent complete or a finish forecast. Can the tracker supply the full loop count per system?
  • Definitions changed mid-series. In the 15 Oct report “CPCLs commenced” became “HW loop references commenced (reconciled tracker total)”. Earlier points may not be comparable.
  • Hand transcription. v1 KPIs are typed from the emails and could carry typos until R10 lands.
  • Distribution. The data names companies and people. Agree who may see the dashboard before sharing it beyond the current mailing list.
  • Hosting approval. Vercel is a third-party host. Confirm that project data may sit there, or keep the site on Deployment Protection with a short invite list.
